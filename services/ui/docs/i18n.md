# Strings

One language: English. What follows is about where the words live,
not about translating them.

## A catalogue, not a translation layer

Every user-visible string goes through `t()` and lives in
`src/frontend/i18n/locales/en.json`. There is no second language and
no language selector.

The catalogue stays anyway, because the alternative is 5,469 strings
spread through 94 components. That costs three things:

- nobody can find a phrase to change it,
- the same sentence gets written three slightly different ways,
- and a reviewer cannot read the product's voice in one sitting.

A key with no string renders as the key. That is ugly and findable,
which beats blank — blank is invisible.

## Adding a string

Add the key to `en.json`, use `t('your.key')` in the component. Group
keys by the surface they appear on, not by the component that happens
to render them; components move.

## There is no language detection

It only made sense when there was something to detect. Leaving it in
would let a stale value in somebody's browser select a language that
no longer exists, which fails as a blank interface rather than an
error.

## If a second language is ever wanted again

It is a real decision, not a file. What has to come with it:

- who writes the translations, and who reviews them — machine output
  is a starting point and is not the same as correct;
- who keeps them in step when English changes, because a stale locale
  renders confidently wrong text to somebody who cannot tell;
- a parity check in the build, so drift fails rather than silently
  falling back to English and looking fine.

Without all three, one language honestly is better than two where the
second is quietly stale.
